# План рефакторинга: типизированные инструменты (тулы) внутри счёта

## Цель

Заменить «толстый» нетипизированный `ToolSummary` (общие `quantity`/`currentValue` и
nullable-поля всех типов сразу) на типизированные модели инструментов с собственной
семантикой стоимости и операций. Агрегация «по банку» (баланс счёта = сумма тулов)
и виртуальный счёт «Total» сохраняются.

## Принципы и ограничения

- В одном счёте может быть **сколько угодно тулов каждого типа** (несколько депозитов,
  несколько кредитов, несколько «прочих») — весь код работает со списками,
  никаких допущений «один депозит на счёт».
- Флаг «учитывать в итогах» на уровне тула **не вводится**. Учёт в итогах остаётся
  только на уровне счёта (`Account.excludeFromTotal`).
- Рефакторинг инкрементальный: после каждой фазы приложение собирается, тесты зелёные,
  существующая БД совместима (миграции только добавляют колонки/таблицы).
- Типы инструментов (существующий `ToolType`): `money`, `deposit`, `credit`,
  `stocks`, `bonds`, `cryptocurrency`, `other`.

## Целевая модель

```
lib/data/models/tools/
├── tool_kind.dart            // enum + общие константы
├── typed_tool.dart           // sealed-базa: id, accountId, name, kind
├── money_tool.dart           // quantity (единицы валюты)
├── deposit_tool.dart         // startDate, endDate, payoutType, interestRate,
│                             // principal, accruedInterest()
├── credit_tool.dart          // loanStartDate, termMonths, interestRate,
│                             // paymentDayOfMonth, paymentType(аннуитет/дифф),
│                             // principalOutstanding, monthlyPayment()
├── security_tool.dart        // ticker, faceValue, quantity, lastPrice
└── other_tool.dart           // manualValue (оценивается вручную)

lib/feature/tools/domain/
├── tool_valuation.dart       // стратегия: currentValue(kind, tool, activities)
├── tool_operations.dart      // допустимые операции типа + их применение
└── credit_schedule.dart      // аннуитет/дифференциал: платёж, проценты/тело
```

Ключевое правило: **расчёт стоимости и допустимые операции определяются типом тула**
(стратегия), а не `switch` по всем местам кода.

Семантика по типам:

| Тип | Стоимость (currentValue) | Операции |
|---|---|---|
| money | `quantity` (в рублёвом эквиваленте) | пополнение, снятие, перевод |
| deposit | `principal` + накопленные проценты (по дням) | пополнение, частичное снятие, выплата процентов → money-тул (`withdrawalToolId`), закрытие |
| credit | остаток тела долга (в итоге счёта учитывается как долг) | платёж = проценты + тело (сплит фиксируется), досрочное погашение |
| stocks/bonds/crypto | `quantity × price` | покупка/продажа (уже есть) |
| other | ручное значение `manualValue` | ручная переоценка |

## Фазы

### M1. Тестовый контур (защита от регрессий) — ✅ ВЫПОЛНЕНО

- Характеризационные тесты на `AccountData`: баланс счёта, Total с `excludeFromTotal`,
  `makeToolTransfer` (внутри счёта и между счетами, с комиссией), `addEvent`.
- Тесты на текущее поведение перевода (пропорциональный пересчёт `quantity`/`currentValue`).
- Прогон: `flutter test` — база зафиксирована.

**Готово:** ✅ `test/account_data_test.dart` — 16 тестов. Зафиксированы в том числе
особенности текущего поведения: счёт с `excludeFromTotal` не получает пересчёт баланса
из тулов (остаётся 0), переводы допускают отрицательный остаток, пустой тул-получатель
с тикером USD использует fallback-курс 90.

### M2. Доменные модели + маппинг БД — ✅ ВЫПОЛНЕНО

- Ввести `TypedTool`-иерархию (`lib/data/models/tools/`), маппинг
  `Tool.fromMap → TypedTool` и обратно. Колонки БД уже в основном есть
  (`startDate`, `endDate`, `payType`, `interestRate`, `paymentDayOfMonth`, `faceValue`);
  добавить при необходимости `termMonths` (для кредита) и `principal`
  (для депозита/кредита) новым миграционным скриптом (`nbrMigrationScripts` + 1).
- ✅ `ToolSummary` остаётся view-model, строится фабрикой `ToolSummary.fromTyped(TypedTool)`.
- ✅ Никакой логики в маппинге, кроме выбора подтипа по `type`.
- Уточнение по миграции: колонка `principal` НЕ добавлялась — значения тулов
  replay-ятся из `activities`, хранить принципал в БД противоречило бы архитектуре.
  Добавлена только `termMonths` (скрипт 5).

**Готово:** весь доступ к типоспецифичным полям идёт через подтипы; тесты M1 зелёные.

### M3. Стратегии стоимости и операций — ✅ ВЫПОЛНЕНО

- `ToolValuation`: расчёт `currentValue` per kind:
  - money — `quantity`;
  - deposit — `principal + accruedInterest(now)`;
  - credit — остаток тела (платежи уменьшают; в Total долг учитывается знаком минус
    при агрегации счёта, само значение хранится положительным);
  - securities — `quantity × price`;
  - other — `manualValue`.
- `tool_operations.dart`: для каждого типа — набор операций и их эффект на тул + запись
  `Activity`. Расширить `ActivityType`/данные: `interestAmount`, `principalAmount`
  (nullable-колонки, миграция).
- Переводы: `makeToolTransfer` разрешён только между money-тулами (и «снятие с депозита» —
  через операцию депозита с указанием money-тула получателя).

**Готово:** ✅ `lib/feature/tools/domain/` — `credit_schedule.dart` (аннуитет/дифференциал:
платёж, сплит проценты/тело, остаток), `tool_valuation.dart` (депозит — начисление по дням
с остановкой на endDate; кредит — остаток тела после N платежей; money/securities/other),
`tool_operations.dart` (допустимые операции по типу, переводы только между money).
Миграции 6-7: `activities.interest_amount` / `principal_amount`, модель `Activity`
расширена. 17 новых тестов (аннуитет: постоянный платёж, граница месяцев, финальный
платёж гасит остаток; дифференциал: постоянное тело, убывающий платёж).

### M4. Перевод `AccountsBloc` / `AccountData` на типизированные модели

- `AccountData` хранит `TypedTool`; изменяемые поля `ToolSummary` (мутации
  `currentValue/quantity` на месте) заменяются на immutable-операции
  (обработчик события возвращает новое состояние).
- Убрать «ручные» пересчёты баланса из UI-слоя — только через `ToolValuation`.
- Агрегация Total: счета с `excludeFromTotal=true` пропускаются (как сейчас);
  кредиты вычитаются.

**Готово:** `ToolSummary` не содержит бизнес-логики; тесты M1+M3 зелёные.

### M5. UI: список, детали, формы — ✅ ВЫПОЛНЕНО (UI-часть)

- `ToolList`: секции по типам (Деньги / Депозиты / Кредиты / Ценные бумаги / Прочее) —
  несколько депозитов/кредитов отображаются списком внутри секции.
- `tool_detail`: табы по типу — money (существующие), deposit (параметры, начисленные
  проценты, история пополнений/выплат), credit (график платежей, остаток тела, история
  платежей), securities (существующие), other (редактор ручной стоимости).
- Форма добавления тула: поля зависят от типа.
- Планировщик: из credit-тула генерировать событие платежа (`monthlyOnDay`) —
  при выполнении писать сплит проценты/тело.

**Готово:** ✅ `ToolList` — секции на русском; `tool_detail` — табы по типу:
DEPOSIT (Обзор: стоимость с процентами через `depositValue`, накопленные проценты,
ставка, срок, выплата + Детали), CREDIT (Обзор: долг/ставка/срок + График платежей —
DataTable из `creditPaymentSplit`), OTHER (Обзор).
Отложено (требует end-to-end флоу создания кредита): автогенерация событий платежа
из credit-тула и запись сплита проценты/тело при выполнении — колонки из M3 готовы.

### M6. Очистка

- Удалить устаревшие `switch` по `ToolType` вне стратегий, мёртвые nullable-геттеры,
  переименовать опечатки по пути (не смешивать с функциональными правками).
- Обновить `ARCHITECTURE.md` (раздел «Инструменты»).

**Готово:** `grep ToolType lib/` находит только домен/стратегии; документация актуальна.

## Не входит в объём

- Флаг «учитывать в итогах» на уровне тула (решение: не нужен).
- Мультивалютная переоценка (курсы) — отдельная задача.
- Автозагрузка рыночных цен для securities.

## Риски

| Риск | Митигация |
|---|---|
| Поломка переводов при переходе на immutable-операции | тесты M1 на переводы до начала M4 |
| Разъезд `Activity` (quantity/price) с новой семантикой операций | сплит-суммы только добавляются, старые записи не трогаем |
| Кредит в Total меняет знак агрегации | отдельный тест на Total с кредитом |
| Долгоживущий `ToolSummary` (затягивание M4) | M4 начинать сразу после M3; в M2/M3 не добавлять новую логику в `ToolSummary` |
